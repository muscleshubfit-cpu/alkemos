**زمن الاستعادة التقديري (RTO) لمشروع Vercel جديد:** 30–60 دقيقة (استيراد + متغيرات + دومينات + فحص دخان) شريطة توفر قيم PayPal/GA/AdSense من لوحاتها.

### 2.4 استقلالية النسخ عن Vercel (نقطة قوة مثبتة)

النسخ الاحتياطي اليومي **لا يعتمد على Vercel نهائيًا**: يعمل بالكامل داخل GitHub Actions ويقرأ من Supabase مباشرة. لو توقف Vercel أو حُذف المشروع **تستمر النسخ اليومية بلا توقف**. كذلك خط إنتاج المدونة (مقالان يوميًا AR/EN) وعامل مهام AI (`process-ai-jobs`) يعملان من GitHub إلى Supabase مباشرة — أي أن توليد المحتوى وطوابيره يستمران حتى أثناء انقطاع Vercel الكامل (الوحيد الذي ينكسر: `vercel-cleanup.yml` لأنه يستدعي Vercel API — وفشله غير مؤذٍ).

### 2.5 مخاطر على استمرارية النسخ نفسه (للرقابة، لا للتغيير الآن)

- **انتهاء صلاحية `BACKUP_REPO_TOKEN`:** التوكنات الرفيعة الدقة (fine-grained) لها تواريخ انتهاء — لو انتهى، تفشل النسخة اليومية بصوت عالٍ (الـ workflow يحمرّ) لكن **لا يوجد تنبيه آلي خارج GitHub** يخبر المالك. (خطورة متوسطة — §9-B3).
- **انزياح جدولة GitHub:** النسخة مجدولة 05:30 UTC لكن التشغيلات الفعلية سجلت 09:31–10:54 UTC (انزياح معروف وموثق في المستودع كنمط منصة). لا يؤثر على الاكتمال اليومي.
- **إلغاء تسجيل الجداول المجدولة بصمت** (نمط موثق في `vercel-cleanup.yml` كـ«Schedule Health Law»): لو توقفت نسخ db-backup فجأة بلا فشل ظاهر، التشخيص الرسمي الموثق: `GET /actions/runs?event=schedule` + تشغيل `workflow_dispatch` يدوي لإعادة التسجيل.

## 7. Cloudflare/DNS Recovery Dependencies — تبعيات Cloudflare وDNS

### 7.1 حالة المنطقة المقيسة (حيًّا، توكن API صالح للقراءة)

- المنطقة `alkemos.com` — **active، full setup** — نيمسيرفرز CF: `sergi.ns.cloudflare.com` / `vida.ns.cloudflare.com`.
- **سجل حاكم:** `A alkemos.com → 76.76.21.21` (**بروكسي CF مفعّل**) — IP أيكاست مشترك لـ Vercel يخدم **أي** مشروع Vercel يُرفق به الدومين → **غالبًا لا يلزم أي تغيير DNS إطلاقًا** عند الانتقال لمشروع Vercel جديد.
- `CNAME www → cname.vercel-dns.com` (بروكسي مفعّل) → تحقق Vercel قد يطلب سجل `_vercel` TXT مؤقتًا (توكن CF API الأول لديه صلاحية DNS للتنفيذ لحظتها).
- إعدادات المنطقة: SSL **Full (Strict)** · Browser-Cache-TTL **0 = Respect Existing Headers** · Always Use HTTPS **on** · Min TLS **1.2** · Brotli **on** · Auto HTTPS Rewrites **on**.
- **قاعدتا الكاش الفعليتان (متحققتان عبر Rulesets API)** — مطابقتان **حرفيًا** لما هو موثق في `docs/TECH_REFERENCE.md §5`:
  1. بطاقات OG: `starts_with(path, "/api/og-image/")` → Edge TTL 86400 / Browser respect-origin.
  2. HTML العام (كل ما ليس api/admin/auth/checkout/dashboard/questionnaires/progress/plans/profile/support/referral/preview/coach وبلا نقطة) → Edge TTL **43200** (12س) / Browser TTL 300.
- **DNS للبريد (خارج نطاق Vercel تمامًا ويبقى كما هو):** Brevo (5 سجلات DKIM/CNAME + SPF + رمز تحقق) · Zoho (3 MX + تحقق + DKIM) · DMARC `p=reject` · تحقق Google Site (GSC).

### 7.2 ماذا يعني هذا للاستعادة

| السؤال | الجواب المقيس |
|---|---|
| هل تُفقد إعدادات CF عند فقدان Vercel؟ | **لا** — المنطقة كيان مستقل تمامًا (حساب CF مستقل، NS عند المسجل). |
| ما المطلوب في CF عند مشروع Vercel جديد؟ | لا شيء إلزاميًا في الغالب (نفس الـ A يعمل). احتمال وحيد: إضافة سجل تحقق `_vercel` TXT لو طلب Vercel إثبات ملكية (نادر مع A المسجل مسبقًا). |
| هل توجد إعدادات CF **غير** موثقة في git؟ | **لا** — القاعدتان + TTL + SSL موثقة بالتفصيل الحرفي في TECH_REFERENCE §5، والتحقق الحي طابقها 1:1 (نموذج توثيق ممتاز). |
| هل يحمي CF الموقع أثناء الانقطاع؟ | جزئيًا: كاش الحافة 12س يخدّم الصفحات العامة والبطاقات (يوم كامل) أثناء فترة الاستعادة — يحافظ على SEO والزوار العاديين للصفحات الثابتة، بينما تنكسر المسارات الديناميكية (الدخول/الداشبورد/الدردشة) فورًا. |
| تبعية إضافية | لا يوجد Page Rules/WAF/Workers في المنطقة (قاعدتا cache فقط) — لا مفاجآت مخفية. |
