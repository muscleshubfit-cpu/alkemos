## 1. الخلاصة التنفيذية

الفحص الشامل للمستودع (كل مسارات API الـ76 + middleware + next.config/vercel.json + workflows + الأصول العامة + سلوك كاش Cloudflare الموثق) خلّص إلى ثلاث حقائق:

1. **البنية التحتية محسّنة أصلًا في أغلبها:** خط أنابيب المدونة يعمل داخل GitHub Actions (صفر وقت دوال على Vercel)، الصور بلا حصة تحسين (`unoptimized`) ومستضافة ذاتيًا بكاش غير قابل للتلف، خرائط الموقع/RSS/llms بـ ISR ساعة، وrobots يحجب `/api/` عن الزواحف، و`NotificationBell` يتوقف عند إخفاء التبويب.
2. **ثلاث فجوات استنزاف حقيقية أُغلقت بالكود في هذا الفريم:** مسار ميت يحرق استدعاءات غير موثقة (`/api/exercise-image`)، وأربع أسطح تستقصي API في التبويبات الخلفية طوال اليوم، و…
3. **الرافعة الأكبر المتبقية خارج الكود:** `/api/og-image/[slug]` مستثنى من قاعدة كاش CF لأنه يبدأ بـ`api/` → كل جلب بطاقة من زواحف السوشيال = دالة Edge + استعلام Supabase + توليد Satori + نقل PNG كامل عبر Vercel. **الحل قرار لوحة تحكم (توصية ت-1 أدناه)** — لم يُنقل المسار في الكود عمدًا لأن عشرات الاختبارات تثبّت صيغة URL المفهرسة أصلاً لدى المنصات.

## 4. توصيات لوحة التحكم — بقرار المالك (§7)

### ت-1 ~~(الأعلى أثرًا): قاعدة كاش Cloudflare لصور OG~~ — **مُنفّذ في VERCEL-USAGE-3 (انظر §8)**
في لوحة Cloudflare (نفس المنطقة، بجانب قاعدة «alkemos cache rules» الحالية) أضف قاعدة Cache Rule جديدة:
- **التعبير:** `(http.request.uri.path contains "/api/og-image/")` — أو أدق: `starts_with(http.request.uri.path, "/api/og-image/")`
- **السلوك:** Eligible for cache · **Edge TTL: 1 day** (البطاقات لا تتغير إلا بتغيير المقال) · Browser TTL: Respect existing (المسار يرسل أصلًا `max-age=86400, SWR 604800`)
- **الأثر:** زواحف السوشيال تعيد الجلب باستمرار (وكل قفزة WhatsApp/Telegram بطاقة = جلب كامل عند الأصل اليوم) → بعد القاعدة: ~99% من هذه الجلبات تُخدم من حافة CF بصفر دوال وصفر نقل من Vercel.
- **قانونيًا:** هذا تغيير لوحة CF → يُنفذ مع تحديث TECH_REFERENCE §5 و SECURITY §10 في نفس الفريم (§5.4/§3.8). **لا يلمس الكود إطلاقًا** — عناوين og:image الحالية تبقى كما هي.

### ت-2: قرار Speed Insights / Web Analytics ~~**ت-2 (بقرار المالك)**~~ — **مُنفّذ جزئيًا في VERCEL-USAGE-2 (انظر §7)**
الـ beacons لا تستهلك حصة **الموقع** (تذهب من متصفح الزائر إلى نطاقات Vercel مباشرة) لكنها تستهلك حصة **المنتجين المقيسين**. السؤال المتبقي على المالك: هل تستخدم لوحة **Web Analytics** في Vercel فعليًا؟ (`<Analytics />` ما زالت مُركّبة — 3.4K/50K فقط من حصتها). إن كان اعتمادك على Google Analytics — أمر إزالتها بريدي وسأنفذها في فريم لاحق.

### ت-3 ~~: رفع Edge TTL لـ HTML (مقايضة SEO)~~ — **مُنفّذ في VERCEL-USAGE-3 (انظر §8)**
الوضع الحالي 3600ث يوازن بين حداثة المحتوى وحمل الأصل. رفعه إلى 4–6 ساعات يقسم استدعاءات الرندر عند الأصل إلى النصف أو الثلث تقريبًا. مقايضة: المقالات الجديدة/التعديلات تظهر أبطأ للزائر العائد عبر PoP بارد. **قرار تسويقي بحت للمالك** — يُنفذ من لوحة CF فقط (تحديث قيمة القاعدة الحالية) مع تحديث التوثيق في نفس الفريم.

### ت-4 (لاحقًا): `getClaims()` بدل `getUser()` في middleware
النمط الحالي يتحقق من الجلسة عبر قفزة شبكة إلى Supabase لكل طلب يحمل كوكيز توثيق. الصيغة الحديثة من @supabase/ssr تدعم `getClaims()` بتحقق JWKS محلي (بلا قفزة). يوفر ~100–300ms من مدة كل دالة لكل طلب موثق. **تغيير حساس أمنيًا → جلسة مركّزة باختبارات مسارات كاملة (OAuth + بريد + admin) بأمر مالك صريح.**

### 8.1 ما نُفِّذ عبر Cloudflare API (المنطقة alkemos.com)

الـ ruleset الحاكم بقي واحدًا — «alkemos cache rules (SEO-GEO-4 2026-09-08)» (phase `http_request_cache_settings`) — وصار يحمل **قاعدتين** بدل واحدة (آخر تحديث 2026-09-16T15:07:35Z):

| # | القاعدة (الوصف الحرفي في اللوحة) | التعبير | السلوك |
|---|---|---|---|
| 1 | `alkemos-public-html-cache (+browser_ttl Phase 189 — deep-audit P2-1); edge TTL 3600->14400s (T-3 VERCEL-USAGE-3 2026-09-16)` | قائمة استثناءات SEO-GEO-4 نفسها (المسارات الخاصة + ما لا يحوي نقطة) | `cache=true` · Edge TTL override **14400ث (4 ساعات — كانت 3600)** · Browser TTL override 300ث — **ت-3** |
