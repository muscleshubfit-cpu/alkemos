# تدقيق مسار تنفيذ توليد المقالات + خطة التعافي المعمارية (Execution-Path Audit & Recovery Plan)

> **التاريخ:** 2026-09-29 · **النوع:** Audit + Implementation Plan فقط — **لم يُعدَّل أي سطر كود أو prompt أو gate أثناء الفحص**. هذا الملف والإضافة على `worklog.md` هما الوحيدان.
> **النطاق (بأمر المالك):** مسار **تنفيذ** التوليد نفسه — من الـ scheduled/manual trigger حتى النشر النهائي: execution prompts · generation orchestrator · model selection / fallback / retry · timeouts · draft assembly · repair/recovery · مسار الفشل · الفرق بين model failure وcontent failure · إعادة استخدام المخرجات الوسيطة. **خارج النطاق:** الـ Gates وEditorial Rules (لا تقييم ولا اقتراح تخفيف لأي بوابة).
> **المنهجية:** قراءة كاملة لطبقة التنفيذ (workflows + run-step + blog-pipeline + ai-provider + routes P0→P5 + blog-queue + dispatch) + **أدلة حية**: سجلات GitHub Actions الفعلية للتشغيلات الفاشلة الأخيرة (`36507693416` · `36489146598` · `36481950930` + تشغيلات AR `35711553282` · `35844856369` · `35982948870`) + استعلام مباشر لجدول `blog_generation_queue` في Supabase (144 صفًا) مع تفكيك `article_bundle` للصفوف الفاشلة نفسها.

## 1. الملخص التنفيذي

**الإجابة المركزية على سؤال المالك («لماذا ينتهي التشغيل بـ markFailed بدل مقال صالح؟»):**

المسار لا ينكسر حيث يفشل النموذج — بل حيث **تنفصل وحدة الفشل عن وحدة الإعادة**. فشل النموذج (timeout / 503 / JSON تالف) يُعالَج محليًا بنجاح عبر retry نفس الخطوة، والدليل أن أغلب الصفوف التي تحمل `error_message` من p1/p2/p4 انتهت حالتها `published`. ما يقتل التشغيلات فعليًا هو صنفان:

1. **فشل بوابة حتمية عند P5 على مُدخل غير قابل للتغيير** — البوابة تفحص `bundle.review.markdown` الثابت، وretry الخاص بـ P5 يعيد نفس الفحص على نفس النص بالحرف، فيفشل 3 مرات متطابقة (أُهدر ~6 دقائق انتظار)، ثم يعلَّم الصف `failed`، ثم "الإصلاح" الوحيد المتاح هو تشغيل جديد كامل من الصفر (P0 جديد → موضوع جديد → توليد كامل) يرمي مقالًا مكتملًا بنسبة ~95%. رسالة الخطأ نفسها تقول `— rerun p2-content` / `— rerun p4-review` لكن **لا يوجد أي مكوّن في النظام ينفّذ هذه الجملة** — هي نص استشاري بلا منفّذ.

2. **عوبة إصلاح Latin للمسار العربي** — لإصلاح ≤32 كلمة لاتينية سائبة، يعيد النظام توليد **المقال كاملًا** بنداء AI ضخم (~9.5k tokens يُقصى به Groq)؛ النموذج المجاني يرتجف: إما timeout متكرر أو يعيد **نصًا إنجليزيًا شارحًا** («we, need, to, replace, latin, words, from, list») بدل المقال المصلَّح، فترفضه البوابة الحتمية (صحيحة) ويموت اليوم كله.

**القياس الحي (آخر أسبوعين، منذ 2026-09-15):** 43 صفًا → 11 فشلًا نهائيًا (**26%**): P4=8 (منها 5 فشل latin-repair validation + 2 نفاد سلسلة + 1 review JSON) وP5=3 (كلها EN بعد تفعيل البطارية الجديدة 09-28: 419 كلمة · 1077 كلمة · FAQ count 0 + anchors). **آخر 3 تشغيلات EN متتالية فشلت كلها في P5** — نفس الصنف، غير قابل للإصلاح بالبنية الحالية.

**الحل الأدنى معماريًا (القسم 8):** حلقة إصلاح داخل نفس التشغيل — P5 يُرجع هدف الإعادة آلة-قابلة-للقراءة (`rerunTarget`)، والـ runner ينفّذها على **نفس صف الطابور** (البنية تدعمها أصلًا: p2/p4/p5 كلها تقبل status `failed`، والـ bundle يحفظ كل المخرجات الوسيطة). ~4 ملفات، بلا migration، وبلا لمس أي gate. يرفع ذلك التنفيذ من «كل فشل = إعادة توليد كاملة» إلى «كل فشل = إصلاح موضع المخلّة فقط»، مع إبقاء كل بوابة كما هي بالبايت.

## 2. خريطة مسار التنفيذ الفعلية (كما هي في الكود اليوم)

```
[Trigger]
 ├─ GHA schedule: blog-post-en.yml (22:00 UTC) · blog-post-ar.yml (05:00 UTC)
 ├─ workflow_dispatch (كوتش/مالك عبر blog-pipeline-dispatch.ts — نفس الـ workflow)
 └─ Vercel cron 23:40 UTC → GET /api/cron/dispatch-pipelines (backstop — يكمّل اليوم فقط)
       └─ GitHub API: workflow dispatch (GITHUB_DISPATCH_TOKEN)

[Execution: GHA ubuntu runner — job timeout 120 دقيقة]
 blog-post-*.yml: P0→P5، كل خطوة: bash run-step.sh <step> 3
   └─ run-step.sh: حتى 3 محاولات، backoff خطي 120s ثم 240s، يلتقط QUEUE_ID في GITHUB_ENV
       └─ run-step.mts (عملية Node مستقلة لكل محاولة): يستدعي route handler داخل-process
           └─ callFreeAIFallbackChain (ai-provider.ts):
                • INTERLEAVED_STRONGEST_CHAIN (8 مداخل) لكن maxModels فعليًا: P1=2 · P2=2 · P4=4 · latin-repair=3
                • حارس Groq 8k TPM: estTokens>7200 ⇒ حذف كل مداخل Groq من السلسلة
                • AI_CHAIN_TOTAL_BUDGET_MS=360s ⇒ effTimeout=floor(360/maxModels) لكل نموذج
                • تدوير القائد (chainCallSeq) = عدّاد في-memory يُصفّر مع كل عملية جديدة
                • dual-key OpenRouter + إعادة محاولة واحدة على empty response (OR فقط)

[State: جدول blog_generation_queue — صف واحد لكل مقالة]
 status: researched → outlined → writing → written → images_done → reviewed → published
 أي throw في الخطوة ⇒ markQueueItemFailed ⇒ status='failed' + error_message (يُحفظ bundle كما وصل)
 p1/p2/p3/p4/p5 كلها تقبل إعادة الدخول على صف status='failed' (نفس الخطوة فقط)
 P0-adopt يتبنى صفوف status='researched' فقط ⇒ أي dispatch جديد بعد فشل لاحق = صف جديد من الصفر

[P5 — deterministic battery (بدون AI)]: word floor 1300 → quota → dup-title
 → splitFaqSection → filterFaqsByRelevance → FAQ-latin gate → insertToolLinks
 → verifyBodyLinks (HEAD) → runP5QualityGates (G2..G6) → Latin body gate → INSERT blog_posts
```

**ثلاث حقائق بنيوية تحكم كل شيء بعدها:**

1. **الـ bundle غير قابل للتغيير عند P5** — P5 لا يستدعي أي نموذج؛ كل بواباته حتمية على `bundle.review.markdown` كما خلّفه P4.
2. **كل خطوة عملية معزولة** — عدّادات السلسلة (`chainCallSeq` · `orKeyCursor`) module-level تُصفَّر مع كل `npx tsx` جديد ⇒ التدوير بين المزودين لا يعمل عبر الخطوات: **أول نداء في كل خطوة يقوده OpenRouter دائمًا**.
3. **إعادة المحاولة لا تعرف نوع الفشل** — run-step.sh يعيد تنفيذ نفس الخطوة بنفس المدخلات مهما كان سبب الخروج 1.

### 3.3 السبب الجذري لحالة «FAQ count 0» (مُثبت من bundle الصف نفسه)

الصف `38f230fb…` (مقالارثون الماراثون) يحتوي `review.markdown` من 1369 كلمة فيه قسم `## Frequently Asked Questions` **مطابق للـ regex** وأسئلة حقيقية بالمحتوى — لكن:

1. **تنسيق الأسئلة نص عادي** (`How soon after a long run…?` في سطر ثم فقرة إجابة) بينما `splitFaqSection` لا يعترف إلا بصيغتين حصريًا: `**سؤال؟**` أو `### سؤال`. النموذج الكاتب (P2) التزم بالصيغة، لكن **نموذج المراجعة (P4 — نموذج آخر) أعاد كتابة القسم وأسقط التمييز bold** — عقد الصيغة يعيش في prompt الـ P2 فقط ولا يُعاد تأكيده في P4 رغم أن P4 يعيد كتابة المقال كاملًا.
2. النتيجة: `faqs=[]` ⇒ fallback إلى `research0.faqs` (10 أسئلة) لكن **`filterFaqsByRelevance` أسقط الكل عشرة** (تقاسم <2 كلمة دالة مع عنوان الماراثون — أسئلة البحث niche-generic عن كرياتين/BCAA/فطائر صيام…). `finalFaqJson = 0` ⇒ G3 يفشل.

**أي أن مقالًا كاملًا جاهزًا للنشر أُعدم لأن رافع الأسئلة (parser) لا يتسع إلا لصيغتين، وبديل الطوارئ لا صلة موضوعية له.** ليست مشكلة Gate — G4/G3 محقان — بل قصور في **طبقة التجميع** (draft assembly) تحت الـ Gate.

### 3.4 نمط الفشل العربي — latin-repair كنقطة انكسار منهجية

من 7 فشل AR النهائية، 5 منها في تمريرة latin-repair وحدها:

- **النداء ضخم بلا داعٍ:** لإصلاح 23–32 token يعاد توليد المقال كاملًا (~9.4k–9.5k tokens payload) ⇒ يُحذف Groq بحارس الـ 8k ⇒ سلسلة من نموذجين على أخطر تمريرة في المسار العربي.
- **فشل صيغة الإخراج:** النموذج (NV-super) يعيد تعليقًا إنجليزيًا عن المهمة بدل `===CORRECTED===` — sentinel parsing لا يجد العلامة فيتعامل مع **الرد الإنجليزي كله** كأنه المقال المصلَّح ⇒ البوابة تكشف 1138–2680 token لاتيني ⇒ رفض صحيح ⇒ فشل اليوم.
- **فشل إدخال عكوس:** حالة 09-17 — المُصلِح أدخل لهجة مصرية صريحة (`إيه×6`) أثناء إصلاح اللاتيني.
- **مفارقة الكلفة:** جدول التعريب (leucine→الليوسين، casein→الكازين، shake→مشروب…) **مكتوب حرفيًا داخل الـ prompt** — يمكن تنفيذ معظمه **حتميًا في الكود بلا أي نداء AI**.

## 4. لماذا الـ fallback الحالي لا يصل إلى مقال صالح

### 4.1 على مستوى السلسلة (callFreeAIFallbackChain)

- **أفضل مزود مُقصى من أثقل النداءات:** Groq/gpt-oss-120b هو الأعلى نجاة حيويًا (85.3% وفق تدقيق 470 تشغيلًا الموثق في الملف نفسه)، لكن حارس `estTokens>7200` يحذفه **كليًا** من P2 (`~8697t`) وP4 (`~11123t`) وlatin-repair (`~9528t`) — أي من النداءات الثلاثة الحاسمة بالضبط. الميزان الفعلي: OR-free (نجاة ~48%) + NVIDIA NIM (503 تحت الحمل في نفس النافذة). الحارس يحسب `maxTokens` كاملاً (6400) بينما مقال 1500–2500 كلمة يحتاج ~2000–3300 output token فقط — **الحساب متحفظ ضدها بلا داعٍ**.
- **التدوير بين المزودين وهمي عبر الخطوات:** `chainCallSeq` في-memory يُصفَّر لكل عملية، وكل خطوة عملية مستقلة ⇒ قائد السلسة OpenRouter في كل خطوة وكل retry. (النية المعلنة في التعليق: توزيع الحمل — غير متحققة في وضع GHA.)
- **ميزانية 360s تُقسّم على maxModels وليس على الحاجة:** P2 = 2×150s. OR-ultra احتاج 113s عندما نجح وabort عند 150s عندما لم ينجح — حدّي. لا يوجد مدخل ثالث لأن الميزانية لا تكفي 3×150s، مع أن job الـ GHA ينتهي عادة في ~28 دقيقة من أصل 120 متاحة، والسابقة الداخلية (`process-ai-jobs.yml`) تستخدم أصلًا **480s**.

### 4.2 على مستوى الخطوة (run-step.sh ×3)

إعادة المحاولة **تعيد السحب من نفس النموذج بنفس الـ prompt** — وهذا يعمل جيدًا للأعطال العابرة (الدليل: صفوف كثيرة فشلت في p1/p2 ثم نشرت). لكنه **لا يقرأ نوع الفشل**: فشل P5 الحتمي يُعاد 3 مرات بالبايت (أدلة §3.2)، وفشل latin-repair الصيغي يُعاد بنداء مراجعة كامل جديد (الأغلى) بدل إصلاح الـ 30 token.

### 4.3 على مستوى التشغيل/اليوم (dispatch backstop)

`computeTopUp` يحتسب التغطية = max(non-failed runs, posts today) ⇒ الفشل لا يغطي ⇒ يُdispatch تشغيل جديد. التشغيل الجديد يبدأ من **P0**، و`findAdoptablePairRow` يتبنى صفوف `status='researched'` **فقط** ⇒ الصف الفاشل (ومعه research/outline/content/images/review كاملة) لا يُتبناه أحد — **يولّد النظام مقالًا جديدًا من الصفر ويرمي القديم**. النتيجة النهائية (تغطية اليوم) تتحقق فعلًا — AR فشل صباح 16/22/23/24 ونشر مساءً بتشغيل كامل ثانٍ — لكن بكلفة مزدوجة وبموضوع مختلف، وهذا هو «إصلاح» النظام الوحيد اليوم: **إعادة توليد، لا إصلاح**.

### 4.4 خلاصة التصنيف (model failure × content failure)

| الصنف | مثال حي | هل يُلتقط اليوم؟ | الآلية الصحيحة |
|---|---|---|---|
| Model-transient (timeout/503/empty) | P2 محاولتا 09-29 | غالبًا نعم (نفس الخطوة) | توسيع السلسلة (مدخل ثالث + Groq) |
| Model-format (JSON تالف/قصير) | p1/p4 أخطاء نُشرت صفوفها | غالبًا نعم | نفس الخطوة + parseJSON المتسامح (موجود) |
| **Content-failure عند P5 (حتمي على مدخل ثابت)** | آخر 3 EN فشل | **لا — أبدًا** | **إعادة تشغيل الخطوة المستهدفة على نفس الصف (غير موجودة)** |
| Content-failure عكسي (المُصلِح يفسد) | latin-repair أدخل إيه×6 / أعاد إنجليزيًا | **لا** | إصلاح موضعي حتمي أولًا + نداء صغير للأثر |

## 5. هل الـ retry يغيّر الاستراتيجية أم يكرر نفس الفشل؟

| طبقة الـ retry | ما تتغير | ما لا يتغير | الحكم بالدليل |
|---|---|---|---|
| داخل السلسلة (fallback بين النماذج) | النموذج (لأقصى maxModels) · المفتاح (dual-key عند quota) · إعادة واحدة على empty (OR فقط) | الـ prompt · الترتيب · القائد (OR دائمًا في GHA) · حذف Groq للأحمال الثقيلة | تغيير محدود فعّال للأعطال العابرة، عاجز عن فك العزلة الثنائية OR+NV |
| نفس الخطوة (run-step ×3) | سحبة نموذج جديدة (random/درجة حرارة) — «dice re-roll» | الـ prompt · السلسلة · المدخل (عند P5: الـ bundle نفسه بالبايت) | **للفشل النموذجي: يعمل** (صفوف p1/p2/p4 نُشرت بعد فشل). **للفشل الحتمي عند P5: تكرار مضمون 3 مرات** (نفس الرسالة بالحرف في السجل) |
| التشغيل/اليوم (backstop) | كل شيء — موضوع جديد، صف جديد، توليد كامل | الجودة/البوابات (كلها تعاد) | «استراتيجية إعادة الضبط الكامل» — أغلى ما يمكن فعله، وفعّال للتغطية اليومية، لكنه ليس إصلاحًا ولا يعلّم النظام شيئًا عن الخلل |

**الجواب المباشر:** الـ retry الحالي **لا يغيّر الاستراتيجية إطلاقًا** — هو re-roll بنفس الخطة. ينجح عندما يكون الفشل صدفة (نموذج/شبكة)، ويفشل حتمًا عندما يكون الفشل محتوى (بوابة على نص ثابت). الرسائل `— rerun pX` المكتوبة في أخطاء P5 هي **تعليمات بلا منفّذ** — لا يقرؤها أي كود.

## 6. ما يمكن إعادة استخدامه بدل إعادة التوليد من الصفر (الموجود فعلًا)

`article_bundle` في الصف الفاشل يحتفظ بكل شيء (تحققت مباشرة في الصفوف الفاشلة):

| المخرج | محفوظ؟ | كلفة إنتاجه | قابلية إعادة الاستخدام |
|---|---|---|---|
| `research0` (كلمات مفتاحية + FAQ) | نعم | نداء chain كامل | فوري — يُعاد استخدامه في أي إعادة P1/P2 |
| `outline` (عنوان/هيكل/LSI/صور) | نعم | 1–2 نداء chain | فوري — إعادة P2 فقط |
| `content.markdown` | نعم | 1–3 نداءات chain (أغلى بند) | **P2 يقبل resume لكن fast-exit يمنع إعادة التوليد المتعمدة — يحتاج `--force`** |
| `images` (3–5 Pexels) | نعم | نداءات API خارجية | فوري — لا يتأثر بأي إصلاح نصي |
| `review.markdown` + report | نعم | 1–4 نداءات chain | P4 يعيد المراجعة على `content` — إصلاح موضعي ممكن |

**الفجوة الوحيدة بين «البيانات موجودة» و«التعافي يحدث» هي غياب المنسّق (orchestration) الذي يعيد تشغيل الخطوة المستهدفة على نفس الصف.** البنية (`status='failed'` قابل لإعادة الدخول في كل route) جاهزة أصلًا — بُنيت لعملية إعادة منفصلة لكن لا أحد يستدعيها بعد P5.

## 7. تداخل التعليمات القديمة والجديدة في مسار التنفيذ (لا في الـ Gates)

1. **ثلاثة أرضيات طول من ثلاثة عصور تعمل معًا:** P2-prompt (1500–2500، القانون الجديد) × P2-code (400 — شبكة صلاحية parse القديمة ما زالت هي الحارس الفعلي) × P5 (1300، الأحدث). الحارس الأضعف هو الذي يحكم سريان التنفيذ، فمقال 419 كلمة «يمر» ويموت متأخرًا. *(وثّق الـ audit السابق C1 الأرقام في الوثائق — هنا الفجوة في كود التنفيذ نفسه.)*
2. **سياسة retry بعصر غير بعصر البوابات:** run-step.sh (2026-08-27، صُممت للأعطال العابرة للنموذج، وتعلّقها التعليقي يقول «matches the previous curl-based workflow policy») لم تُمسّ بعد أن غيّرت بطارية P5 (09-28) دلالة الفشل من «عابر» إلى «حتمي على مدخل ثابت».
3. **فلسفة التعافي المعلنة قديمة:** تعليقات P5 نفسها تصف الآلية: «fail honestly → markFailed → the 23:40 backstop tops the day's slot up with a fresh run» — أي أن **إعادة التوليد الكامل هي «الإصلاح» الرسمي الموثق**. هذا كان منطقيًا قبل اكتمال الـ bundle؛ اليوم يرمي مخرجات صالحة.
4. **latin-repair نمط «إعادة توليد كاملة» قديم:** صُمم قبل فلسفة البوابات الموضعية؛ البوابات الجديدة موضعية (token، anchor، FAQ) لكن الإصلاح ما زال full-text regeneration — نفس المهمة بنِسَب payload أضخم 10× من اللازم.
5. **عقد صيغة FAQ يعيش في P2 فقط:** P2 يفرض `**السؤال؟**` لكن P4 (نموذج آخر يعيد كتابة النص كاملًا) لا يُذكَّر بالصيغة — التعليمات القديمة (P4 instruction 6: «keep the FAQ section… answers stay plain text») لا تعيد تثبيت صيغة السؤال، بينما الـ parser عند P5 يشترطها حصريًا. النتيجة الموثقة في §3.3.
6. **رسائل `rerun pX` — تعليمات جديدة بلا منفّذ:** أُضيفت إلى أخطاء P5 في المرحلة الأخيرة كنصيحة للقارئ البشري؛ لم تُحوَّل عقدًا قابلًا للتنفيذ في الـ runner.
7. (إيجابي) **لا تعليمات ميتة فعّالة في مسار التنفيذ:** حراس `check-stale-refs.sh` + canaries تمنع رجوع مسارات v1 — التداخل الحقيقي ليس في الميت بل في تعايش طبقات حية من عصور مختلفة (نفس نتيجة الـ audit السابق، مطبقة هنا على طبقة التنفيذ).

## 8. أقل تعديل معماري يجعل المسار قادرًا على التعافي والإكمال: **حلقة إصلاح داخل التشغيل (In-Run Repair Loop)**

### 8.1 المبدأ

الفشل الحتمي عند P5 ليس حدثًا نهائيًا بل **توجيه إصلاح**: الخطأ نفسه يسمّي الخطوة المسبّبة. اجعل الـ runner ينفّذ التوجيه على نفس الصف — مرة أو مرتين كحدّ أعلى — قبل الاعتراف بالفشل. **لا يُمسّ أي gate ولا يُخفَّف أي عتبة؛ يُمسّ فقط من يعالج الفشل ومتى.**

### 8.2 التصميم الأدنى (4 ملفات، بلا migration)

```
(A1) p5-publish/route.ts — عقد إعادة تشغيل آلة-قابل-للقراءة:
     في جسم الخطأ 500: { error, rerunTarget: "p2-content" | "p4-review" | null }
     الخريطة الحتمية (بلا ذكاء):
       word-floor  ──────────────→ "p2-content"
       FAQ count / anchors / G4 authority / quoted-phrases → "p4-review"
       latin body / link-verify (غير قابل للإصلاح المحلي) → "p4-review"
       quota / duplicate-title → null (ليست فشل إصلاح — سلوكها الصحيح الحالي)

(A2) run-step.mts — ترجمة خروج 3 + إخراج الهدف:
     عند ok:false و rerunTarget موجود ⇒ exit code 3 مع سطر `RERUN_TARGET=pX` في stdout

(A3) run-step.sh — حلقة الإصلاح (بدل التكرار الأعمى عند exit 3):
     budget ≤ 2 دورة: نفّذ الهدف (بنفس QUEUE_ID) ثم أعد الخطوة الفاشلة
     دورة p2 تتطلب (A4)؛ بعد نفاد الميزانية ⇒ فشل صادق كما اليوم
     (خطوات P0–P4 تبقى على سلوك ×3 الحالي — فهو يعمل لها)

(A4) p2-content/route.ts — علم `?force=1`:
     يتخطى fast-exit الـ resume ويولّد المحتوى من جديد فوق نفس الصف
     (يحافظ على research0/outline/images؛ يُستبدل bundle.content فقط)
```

**الاختياري عالي القيمة (نفس الروح، طبقة واحدة):**

```
(B1) p4-review وضع الإصلاح: عند وجود ?repairDiagnostics=… تُدمج أسماء البوابات
     الفاشلة في مقدمة prompt المراجعة كتشخيص («أصلح تحديدًا: الأسئلة الشائعة
     بصيغة **سؤال؟**؛ الرابطان التاليان anchors غير قواعدية…») — تغذية راجعة
     بالتشخيص لا قانون تحريري جديدًا (التزامًا بقانون منع تكديس الطبقات)
(B2) رفع P2 code floor من 400 إلى ~1200: إعدام المقال القصير في أرخص نقطة
     (تشديد لا تخفيف — يجعل floor التنفيذ يطابق floor النشر)
(B3) توسيع splitFaqSection بقبول سطر سؤال نصي منتهٍ بـ ?/؟ يليه فقرة إجابة
     (صيغة ثالثة للرفع فقط — G3 كما هو بالبايت؛ يستعيد أسئلة موجودة فعلًا
      في المتن بدل إعدام المقال كما في §3.3)
```

### 8.3 لماذا هذا هو «الأقل» تحديدًا

- **البنية موجودة أصلًا:** كل الـ routes تقبل `status='failed'`، والـ bundle يحفظ المخرجات — العمل الجوهري هو تمرير `rerunTarget` من P5 إلى الـ runner (سطر JSON + exit code + حلقة bash).
- **لا يحتاج** DB migration، ولا بوابة جديدة، ولا تعديل أي عتبة، ولا مزودًا جديدًا.
- **يحترم كل القوانين الحالية:** markFailed يبقى (عند نفاد الميزانية)؛ الـ backstop يبقى (شبكة اليوم الأخيرة)؛ قانون المقالة/اليوم لا يُمس (الإصلاح على نفس الصف لا يستهلك حصة جديدة)؛ الفشل الصادق يبقى الفشل الصادق.
- **أثره مباشر على سجل الفشل الحي:** حالات P5 الثلاث الأخيرة (§3.1) كانت ستُصلَح داخل تشغيلها: 419/1077 كلمة ⇒ إعادة P2 فقط (research/outline/images معاد استخدامها)؛ FAQ-0 ⇒ (B3) يحلها حتميًا بلا AI، وبدونه تُصلَح بإعادة P4 بتشخيص.
