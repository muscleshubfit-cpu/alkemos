المخاطر الحقيقية المتبقية تتركز في **4 عناقيد**:

## 5. ما تم التحقق من سلامته (إيجابيات موثقة بالكود)

هذه ليست مجاملة — نتائج فحص فعلي بالدليل، تُدرج لتوثيق الحدود الآمنة التي لا تحتاج عملًا:

- **المصادقة**: صفر استخدام لـ`getSession()` بكود API (المصدر الوحيد عميل تجريبي محلي) — كل الخادم عبر `getUser()` + تحميل الدور؛ كل مسارات `/admin/*` (100%) تتحقق من الدور خادميًا؛ فحوص IDOR/ملكية حيث يجب (plans · ai/jobs · support · coach-whatsapp · activate).
- **أسرار CRON**: كل مسارات cron الثمانية + dispatch-pipelines + evo/followup تستخدم `verifyCronAuth` (timing-safe، fail-closed) — استثناء واحد موثق (S-10).
- **PayPal webhook**: تحقق توقيع عبر واجهة PayPal الرسمية؛ لا يكتب أموالًا أبدًا (log-only)؛ عكس الاسترداد idempotent.
- **اقتصاديات المحفظة**: خصم-first عبر `coach_adjust_wallet` RPC (صف-مقفل، لا سالب) + استرداد عند فشل التفعيل + عمولات idempotent على paymentId (قيد فريد DB + معالجة 23505) + شحن المحفظة محمي الإعادة **المتتابعة** بفحص UUID5 — الإعادة **المتزامنة** تبقى ثغرة (فحص قراءة-ثم-فعل بلا قيد فريد — S-01)، وذراع الاشتراك بلا حماية أصلًا (S-01).
- **الرفع والملفات**: قوائم MIME سماح + شم البايتات السحرية + سقف 5MB + مسارات يعيد بناءها الخادم + سقوف لكل مستخدم؛ `/api/file` يرفض `..` ويجيز مالك-البادئة أو طاقمًا فقط.
- **RLS**: كل CREATE TABLE يتبعه ENABLE ROW LEVEL SECURITY (61 عبارة/41 ملفًا — بما فيها استرجاع 0056/0088 الحرفي بعد حادثة المرحلة 61)؛ كل دوال SECURITY DEFINER (30+) تثبّت `search_path`؛ السجلات الحساسة RLS-on بلا سياسات عميل.

### 6.4 تصميم W0-3 (جاهز لموافقة §7) — idempotency ذرية لمسار PayPal

**المبدأ:** نفس الأنماط المثبتة أصلًا بالمستودع — قيد فريد + معالجة 23505 (affiliate 0015/0057) واستهلاك ذري (0042) — لكن الحكم ينزل من التطبيق إلى **قاعدة البيانات**.

**ميجريشن 0098** (ملف واحد idempotent بقانون §6 كاملًا):
1. `alter table public.subscription_requests add column if not exists paypal_order_id text;`
2. `create unique index if not exists uq_subscription_requests_paypal_order on public.subscription_requests (paypal_order_id) where paypal_order_id is not null;` — **الإدراج هنا هو القفل الذري**؛ كل الصفوف التاريخية NULL فلا تعارض ولا backfill.
3. `create unique index if not exists uq_coach_wtxn_topup_ref on public.coach_wallet_transactions (ref_id) where ref_id is not null and kind = 'topup';` — يحسم سباق المحفظة المتزامن (تعديلات الأدمن تدخل `ref_id=null` وتفعيلات المدرب `kind='activation'` فلا يتأثر أي مساس آخر — متحقق بالكود).
4. RPC جديد `capture_paypal_subscription(p_user_id, p_tier, p_months, p_amount_usd, p_order_id, p_full_name)` (SECURITY DEFINER + `search_path` مثبت كنمط 0042): يدرج صف `subscription_requests` (status='approved' + `paypal_order_id`) داخل **استثناء مُدار** — انتهاك الفريد 23505 ← يقرأ الصف الموجود ويعيد «مُعالَج مسبقًا»؛ ثم ينفذ منطق `extend_subscription` — **كل ذلك معاملة واحدة**: فشل التمديد يُرجع الإدراج كله (لا قفل بلا أثر ولا حالة مسمومة تمنع إعادة المحاولة).
5. `coach_adjust_wallet`: التقاط 23505 على إدراج السجل ← إرجاع الرصيد الحالي كـ«مُشحن مسبقًا» (تعديل مضيف لا يغير السلوك العادي).

**فريم الكود (نفس كوميت الميجريشن — مهمة واحدة):** ذراع الاشتراك يستبدل الندائين المنفصلين (extend + سجل الدفع) بنداء الـRPC الواحد + استجابة نجاح idempotent بنفس شكل النجاح الأصلي عند «مُعالَج مسبقًا» (الإشعارات/العمولة تُنفَّذ بعده فقط — العمولة محمية بقفلها الخاص أصلًا)؛ ذراع المحفظة يُبقي الفحص السريع ويعالج 23505 كحسم سباق. **كاناري:** إعادة متتابعة = 200 idempotent · إعادة متزامنة = الخاسر 23505→200 idempotent · فشل التمديد يُرجع القفل (لا صف ولا تمديد) · فحص ref_id للمحفظة تحت التزامن.

**مخاطر وملاحظات تنفيذ:** الميجريشن يُطبَّق آليًا بدفع الكوميت (تكامل Supabase-GitHub) والنشر يتبعه بدقائق — نفس نمط 0042 («تحديث المستدعين بنفس الكوميت»)؛ نافذة عدم توفر الـRPC نظريًا ثوانٍ قبل اكتمال النشر — السابقة المستودعية تقبل هذا الاقتران. **الاسترجاع:** revert الكوميت + إسقاط الفهرسين والعمود والـRPC يدويًا (كلها مضيفة). **SECURITY.md يُحدَّث بقانون §7.**
