## 2. نتائج التدقيق — ما الموجود، وما المشكلة

### 2.1 جواب مباشر: هل النسخ اليومي ضروري؟ — **نعم، إلزامي**

الدليل المقيس: Supabase Free لا يوفر **أي** نسخة احتياطية (`backups: []`, `pitr_enabled: false`). لو حُذف `db-backup.yml` اليوم لأصبحت قاعدة البيانات وصور المستخدمين **بلا أي نسخة على الإطلاق** — أول bad migration أو حذف جدول خطأ = فقدان نهائي. النظام اليومي ليس رفاهية ولا تكرارًا؛ هو خط الدفاع الوحيد القائم.

### 2.2 هل توجد نسخة احتياطية مكررة بلا فائدة؟

لا يوجد تكرار حرفي (لا artifacts، لا مستودع نسخ ثانٍ، لا snapshot مزدوج). الموجود أدق من وصف «التكرار»: **تراكم بلا قاعدة** — 29 لقطة DB كاملة + 14 نسخة ملفات كاملة في working tree مع أن قيمة الاستعادة اليومية تتركز في آخر أيام قليلة، والباقي «تاريخ» كان يمكن اختزاله بأسبوعي/شهري. تداخل وظيفي وحيد: `storage-inventory` (جرد) مقابل `storage-backup` (ملفات فعلية) — الجرد ~1 KB يوميًا وقيمته رصد النمو، يُبقى عليه (رخص ولا يستحق تعطيل آلية عاملة).

### 2.3 العوائق المثبتة (ترقيم BS — Backup Strategy؛ تمييزًا عن ترقيم B1–B9 في تدقيق 2026-09-20)

| # | العائق | الدليل المقيس | الأثر |
|---|---|---|---|
| **BS-1** | **كل النسخ داخل حساب GitHub واحد** (نفس عائق B2 القائم منذ 2026-09-20) | alkemos (العام) + musclehubeg-backups (الخاص بكل الـ PII) تحت `muscleshubfit-cpu`؛ المرآة الخارجية المجهزة (P0-1) ساكنة 13+ يومًا لعدم إكمال إعدادها | فقدان الحساب (ban/اختراق/حذف عرضي) = فقدان الكود **و** النسخ معًا — عطل واحد يمسح كل شيء |
| **BS-2** | **لا Retention إطلاقًا** | 29 + 14 + 14 مجلدًا يوميًا متراكمًا، ولا يوجد أي workflow حذف/تنظيف في المستودعين | «30 نسخة كاملة» صحيحة ومتزايدة بلا سقف؛ النمو اليومي الخام ~14 MB يقفز خطيًا مع كل محتوى جديد (كل صف/ملف جديد يكبّر **كل** اللقطات اليومية بعده) |
| **BS-3** | **git يُستخدم مخزن كائنات** (منصوص حرفيًا في تعليق `storage-backup.yml`) | سقف الطوارئ 20k كائن / 1 GiB = توقف صاخب عند النمو، لا استراتيجية | عند تجاوز الحد تتوقف نسخة الملفات يومًا ما بلا خطة بديلة جاهزة |
| **BS-4** | **لا نسخة off-site إطلاقًا** | `EXTERNAL_MIRROR_TOKEN` ومتغيرا الـ mirror غير موجودين (قياس مباشر)؛ R2 غير مفعّل/بلا صلاحية | كل النسخ جغرافيًا وتنظيميًا داخل GitHub فقط |
| **BS-5** | **تاريخ git يحتفظ بالـ PII للأبد** | الحذف من working tree (Retention) يوقف نمو الاستنساخات لكن لا يصغّر التاريخ | مقبول مؤقتًا (مستودع 10 MB)؛ يلزم قرار منفصل إذا تجاوز المستودع ~1 GB |

### 2.4 تقييم المُستهلك اليوم

التكلفة النقدية اليوم = **$0 فعلًا** (ريبو عام → دقائق مجانية؛ صفر artifacts؛ git غير مفوتر). مشكلة النظام الحالي **ليست الفاتورة** بل: غياب سقف النمو (BS-2/BS-3) + التمركز (BS-1/BS-4). أي خطة «تحسين» تعطّل النسخ اليومي تحمي الفاتورة وتُعرّض البيانات — الأولوية معكوسة تمامًا.

## 3. التصميم المقترح — الآلية الموحدة (Free/Hobby أولًا)

### 3.1 المبادئ الحاكمة

1. **فصل الطبقات:** GitHub الخاص = طبقة تشغيلية قصيرة المدى (استعادة سريعة لبضعة أيام) · Off-site (R2) = طبقة نجاة طويلة المدى (تُنجو من فقدان GitHub نفسه).
2. **لا إعادة بناء لما يعمل:** النسخ اليومية الثلاث تبقى كما هي بلا تعديل — تُضاف طبقتان فوقها (Retention + Off-site)، لا تُستبدل.
3. **Free/Hobby صارمة:** GitHub $0 (ريبو عام) · Supabase Free بلا لمس · Vercel Hobby بلا لمس · R2 ضمن فئتها المجانية (10 GB + صفر رسوم egress).
4. **قانون PII:** كل ما يغادر GitHub يُشفَّر جانب العميل إلزاميًا (المستودع الخاص يحمل أشد أنواع PII — صور وإيصالات)، والوجهة bucket خاص بتوكن ضيق النطاق.

### 3.2 البنية (مخطط تدفق)

```
  Supabase (DB + Storage)                GitHub: alkemos (public code)
  ─────────────────────                  ───────────────────────────
     │  يوميًا 05:30 / 05:45 / 06:00 UTC        │
     ▼                                          │
  ┌─────────────────────────────────────────────┴───┐
  │  musclehubeg-backups (PRIVATE, نفس حساب GitHub) │  ← كما هو اليوم (لا تغيير)
  │   snapshots/ · storage-backups/ · storage-inventory/ │
  └───────────────┬─────────────────────────────────┘
                  │  ① أسبوعيًا: backup-retention (GFS prune داخل المستودع الخاص)
                  │ ② أسبوعيًا: offsite-r2-upload — أرشيف tar.gz + تشفير (age/AES-256)
                  │ ③ شهريًا: git bundle (alkemos + musclehubeg-backups) + تشفير
                  ▼
  ┌───────────────────────────────────────────────┐
  │  Cloudflare R2 — bucket خاص alkemos-backups  │   ← الجديد (بأمر مالك)
  │   weekly/ · monthly/   ← GFS prune آلي        │   egress $0 · ضمن 10GB مجانًا
  └───────────────────────────────────────────────┘
                  │  ④ ربع سنويًا: restore-drill من R2 (تنزيل → فك تشفير → sha256 → dry-run)
                  ▼
  إثبات قابلية الاستعادة من خارج GitHub بالكامل
```

### 3.3 خيار التخزين الخارجي: لماذا R2 (ولماذا يبقى الـ git mirror خيارًا بديلًا)

| المعيار | Cloudflare R2 (المقترح) | Git mirror خارجي (P0-1 المجهز) |
|---|---|---|
| تجهيز المالك | تفعيل R2 (يتطلب وسيلة دفع) + bucket + توكن Object-RW | حساب جديد على GitLab/Bitbucket/GitHub آخر + مستودعان + توكن |
| التكلفة | **$0** حتى 10 GB (و$0.015/GB بعدها) + **صفر رسوم egress** | $0 |
| ما يُخزَّن | أرشيفات مشفرة انتقائية (DB + ملفات + bundles) — أصغر بصمة | تاريخ git كامل يومضغط أعلى (mirror كامل دائمًا) |
| Retention | GFS آلي بالمفاتيح — بسيط | تاريخ git يتراكم كاملًا (تنظيفه = rewrite خطر) |
| قابلية الاستعادة | تنزيل + فك تشفير + سكربتات الاستعادة الموجودة | git clone مباشر |
| نقطة ضعف | توثيق كامل عبر S3-API (rclone) داخل Actions | **جاهز 100% اليوم** (`external-mirror.yml` + دليل الإعداد) |

**التوصية:** R2 كمسار أساسي (أصغر بصمة + GFS نظيف + egress مجاني)، مع اعتبار `external-mirror.yml` الجاهز **خطة بديلة فورية** إن قرر المالك عدم وضع وسيلة دفع على Cloudflare — كلاهما يغلق BS-1/BS-4؛ لا يُشغَّلان معًا إلا بقرار مالك (ازدواجية استهلاك زهيدة لكنها غير ضرورية).

### 3.4 Retention المقترح — GFS (Grandfather-Father-Son) بدل 30 نسخة كاملة متراكمة

| الطبقة | القاعدة | DB snapshots | Storage backups | الجرد (census) |
|---|---|---|---|---|
| **Daily (ابن)** | آخر 7 أيام فقط | 7 | 7 | 7 |
| **Weekly (أب)** | نسخة كل أحد — آخر 5 أسابيع | 5 | 5 | 5 |
| **Monthly (جد)** | أول يوم بالشهر — آخر 6 أشهر | 6 | 6 | 6 |
| **الحصيلة القصوى في working tree** | | **18 نسخة** (بدل 29+ غير المنتهية) | 18 | 18 |

- **على R2:** أسبوعي احتفظ بآخر **8** · شهري احتفظ بآخر **6** (بundles الكود شهرية فقط).
- **الحصيلة العملية:** من متوسط تراكم 30 نسخة/شهر متصاعد → سقف ثابت 18 نسخة (working tree)، وأسوأ حالة فقدان بيانات = يوم واحد (النسخ اليومية موجودة دائمًا).
- **قاعدة الحذف آمنة:** الحذف من working tree فقط عبر workflow مخصص؛ تاريخ git يبقى كما هو (BS-5 مؤجل بقرار منفصل إذا لزم).
- **صمّ القواعد كمتغيرات** (نسق `notifications-prune.yml` القائم): `BACKUP_RETENTION_DAILY=W` قابل للضبط من Settings بلا تعديل كود.

### 3.5 بنية الـ Bucket والتشفير (تصميم، لا تنفيذ)

```
alkemos-backups/                      (bucket PRIVATE واحد)
  weekly/  2026-W40.db.tar.gz.age     (آخر لقطة DB + نسخة الملفات، مضغوطة مشفرة)
  monthly/ 2026-10.db.tar.gz.age      (نفس المحتوى بتاريخ الشهر)
  monthly/ 2026-10.alkemos.bundle.age (git bundle كامل التاريخ للريبو العام)
  monthly/ 2026-10.backups.bundle.age (git bundle للمستودع الخاص)
```

- **التشفير إلزامي قبل مغادرة GitHub** (age أو openssl AES-256) — مفتاح مستقل `BACKUP_ENCRYPTION_KEY` في Secrets، **مع قرار حفظ خارجي للمفتاح** (مدير كلمات مرور لدى المالك): المفتاح داخل GitHub وحده يعني فقدانه مع فقدان الحساب — نفس العطل الذي نعالجه.
- **الرفع عبر rclone/S3-API** إلى `https://<account_id>.r2.cloudflarestorage.com` بمفاتيح R2 (Access Key ID + Secret) بتوكن **Object Read & Write على الباكيت هذه فقط** — لا صلاحيات Account/Zone إطلاقًا.
- **الأسرار الجديدة المطلوبة (3 فقط):** `R2_ACCESS_KEY_ID` · `R2_SECRET_ACCESS_KEY` · `BACKUP_ENCRYPTION_KEY` — كلها تُوثق مصادرها في `docs/RECOVERY-SECRETS-SOURCES.md` عند التنفيذ. الأسرار القائمة (`BACKUP_REPO_TOKEN`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SUPABASE_URL`) تُعاد استخدامها كما هي — لا تدوير ولا لمس.

## 5. خطوات التنفيذ اللاحقة — **لا يُنفَّذ أي منها الآن** (كلها بأمر مالك)

| المرحلة | المحتوى | الجهة | الاعتماديات |
|---|---|---|---|
| **R2-0 (قرارات مالك)** | ① اعتماد R2 مسارًا أساسيًا (أو الـ git mirror بديلًا) ② تفعيل R2 + وسيلة الدفع ③ قرار حفظ مفتاح التشفير خارج GitHub ④ اعتماد الأسرار الثلاثة الجديدة | المالك | — |
| **R2-1 (تجهيز مالك)** | إنشاء bucket خاص `alkemos-backups` (لا публичية، لا دومين مخصص) · إنشاء R2 API Token بصلاحية Object Read & Write على الباكيت فقط · إضافة الأسرار الثلاثة في Secrets | المالك | R2-0 |
| **R2-2 (Retention)** | Workflow أسبوعي `backup-retention.yml` (السبت 03:30 UTC — نافذة هادئة بعد `notifications-prune`) + سكربت GFS prune داخل المستودع الخاص، باستخدام `BACKUP_REPO_TOKEN` القائم | تنفيذ آلي داخل alkemos | R2-0 فقط (لا يحتاج R2) |

| **R2-4 (إثبات)** | دريل استعادة ربع سنوي من R2 (تنزيل → فك تشفير → تحقق sha256 → dry-run بـ `db-restore.mjs`/`storage-restore.mjs`) + تحديث `docs/RECOVERY-MIRROR-SETUP.md` (تحويل الـ mirror لخطة بديلة أو إيقافه بقرار) + README المستودع الخاص + `docs/RECOVERY-SECRETS-SOURCES.md` | تنفيذ آلي + توثيق | R2-3 |

## 6. ما التُزم به في هذا الإطار (تدقيق قراءة فقط)

لم يُنفَّذ ولن يُنفَّذ قبل أمر مالك: أي backup أو restore أو drill · إنشاء/تعديل أي bucket · تعديل/إضافة/حذف أي workflow أو secret أو variable · أي مساس بـ Production أو DNS أو Vercel أو Supabase أو Cloudflare. الإطار كله = استعلامات API للقراءة + هذا الملف الواحد على `main` بعلامة `[vercel skip]` (نمط التوثيق القائم — آخر docs-commit أنتج نشرًا CANCELED بلا خدمة، مؤكد في `docs/VERCEL-BACKUP-MIGRATION-PLAN-2026-10-03.md` §1).
